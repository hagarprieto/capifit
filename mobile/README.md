# CapiFit — App (mobile)

React Native + Expo (SDK 58) com Expo Router. Código em `src/`; rotas em `src/app/`.

## Comandos

```bash
npm install            # dependências (se faltar algum pacote, use `npx expo install <pacote>`)
npm start              # servidor de desenvolvimento (abra com o Expo Go ou um build de desenvolvimento)
npm run check          # tokens + TypeScript + lint + regras do projeto + testes (o mesmo que o CI roda)
npm run tokens         # regenera src/design-system/tokens.generated.ts a partir de docs/08_design_tokens.json
npm run api:types      # regenera src/api/schema.generated.ts a partir de docs/07_openapi.yaml (o check confere se está em dia)
npm run mock:api       # servidor mock do contrato em http://localhost:4010 (Prism), para trabalhar sem a API
```

## Regras do projeto

- **Cores só pelos tokens.** `docs/08_design_tokens.json` é a fonte; o tema é gerado (`npm run tokens`) e o lint reprova
  cor literal (hex, `rgb()`) em `src/` (DS-02).
- **Texto só pelo catálogo.** Toda string visível vem de `src/i18n/pt-BR.ts` via `t()`; o lint reprova texto fixo no JSX.
- Use `npx expo install` (não `npm install`) para pacotes do Expo, para obter a versão compatível com o SDK.
- Não edite `ios/` nem `android/` (gerados). Configuração nativa fica em `app.json`.

## API e autenticação

- **URL da API:** `EXPO_PUBLIC_API_URL` (ver `.env.example`; variáveis `EXPO_PUBLIC_*` ficam visíveis no app, nunca coloque segredo). Emulador Android acessa o PC por `http://10.0.2.2:PORTA`.
- **Tipos do contrato:** `src/api/schema.generated.ts` é gerado do OpenAPI (não edite). Mudou o contrato? Rode `npm run api:types` e commite; o CI reprova se estiver defasado.
- **Cliente:** `src/api/client.ts` desembrulha o envelope, devolve `ApiError` (código, campos, `request_id`, `Retry-After`), tem tempo limite e, em 401, renova o token UMA vez e repete a chamada com a mesma chave de idempotência.
- **Sessão:** tokens ficam só no armazenamento seguro do aparelho (`expo-secure-store`: Keychain/Keystore), nunca em log nem em estado de tela. `src/auth/authCore.ts` renova com uma chamada por vez; o app restaura a sessão ao abrir, inclusive sem rede (o treino não depende da conexão). O identificador do aparelho é criado uma vez e sobrevive ao logout.
- **Rotas por sessão:** `src/app/_layout.tsx` usa `Stack.Protected`: sem sessão só as telas de entrada (`boas-vindas`, `entrar`, `cadastrar`, `recuperar`); com sessão a área logada. O link do e-mail abre `redefinir-senha?token=…` (esquema `capifit://`). O guard só esconde telas: a autorização é do servidor.

## Banco local (E08-01)

- **O que é:** SQLite do aparelho (`expo-sqlite`) em `src/data/local`. Guarda a sessão de treino (exercícios, séries e pausas no mesmo formato da API), a **fila de operações** a enviar (`/sync/push`) e um cache JSON por chave. Tudo é separado por usuário: dois usuários no mesmo aparelho nunca se enxergam.
- **Migrações:** `migrations.ts`, versão em `PRAGMA user_version`. Cada passo roda em transação com a troca da versão; se falhar, volta atrás. **Nunca edite uma migração publicada**, acrescente outra ao fim. Banco mais novo que o app (volta de versão) não é alterado: lança `DatabaseTooNewError` para não apagar dados de treino.
- **Repositórios:** `sessionsRepo` (salvar a sessão inteira de uma vez, abrir a em andamento, histórico, atualizar série, concluir, marcar como confirmada), `queueRepo` (ordem por `sequencia`, `operacao_uuid` estável, enviando/aplicada, rejeitada e conflito ficam para revisão, retomar o que ficou "enviando" se o app fechou) e `cacheRepo`.
- **Abrir:** `openLocalDb()` (`open.ts`) abre uma vez, liga chaves estrangeiras e migra. Os repositórios só dependem da interface `LocalDb`; nos testes ela vem do `node:sqlite` em memória (`memoryDb.ts`, nunca vai para o pacote do app), então as consultas são testadas em SQLite de verdade. O CI usa Node 22 por isso.
- **Envio da fila (E08-03):** `src/data/sync`. `buildOfflineSession` monta a sessão (de uma ficha ou avulsa) com **todos os UUIDs gerados no aparelho** (RG-020) e o corpo da operação `criar` no formato do `/sync/push`. `createSyncEngine().flush()` manda a fila em lotes de até 50, na ordem de criação, com `dispositivo_uuid` e `sequencia_cliente`: **aplicada** sai da fila; **conflito** e **rejeitada** ficam com o motivo para revisão (E08-05); sem rede, 5xx ou limite de requisições, o lote volta a pendente e o reenvio usa as mesmas identidades; lote recusado inteiro (4xx) fica visível como rejeitado; operação sem resposta volta para a próxima rodada; só um envio por vez. A sessão só vira "confirmada" quando nenhuma operação dela está esperando ou em revisão.
- **Cache do treino do dia (E08-02):** `src/data/cache/todayWorkout.ts` guarda o programa ativo (fichas, exercícios, séries com UUIDs e metas) e o último registro de cada exercício. O Início passa a usar `loadActiveWithCache`: com rede, mostra o do servidor e atualiza a cópia em segundo plano (registros novos substituem os antigos; se a busca de registros falhar, os antigos ficam); sem rede, com servidor fora do ar ou limite de requisições, mostra a cópia e avisa de quando ela foi salva; sem programa no servidor, a cópia é apagada. Erro de permissão ou de contrato nunca é escondido pela cópia. `LocalDataProvider` abre o banco quando há usuário conectado; se ele não abrir, o app segue só online.
- **Executor com o aparelho em primeiro lugar (E07-11):** `src/data/offline/localFirstWorkoutApi.ts` tem a mesma interface da API do treino e é a que as telas usam quando o banco local abriu (`useWorkoutApi`). Regra: treino que o servidor já conhece e sem pendências vai direto ao servidor, e **só uma falha de conexão** faz o registro ser salvo no aparelho e entrar na fila; treino criado sem rede, ou com operações ainda na fila, grava **tudo** local e enfileira **na ordem** (o servidor nunca recebe uma série de sessão que ainda não conhece). Erro do servidor (ex.: treino já encerrado) continua aparecendo como erro. Sem rede dá para: começar um treino de ficha (usa a cópia do programa) ou avulso, concluir série, acrescentar série e finalizar; últimos registros e metas vêm da cópia. A fila é enviada ao abrir o app e quando ele volta ao primeiro plano, e logo após cada registro. **Recuperação:** ao reabrir o app (inclusive depois de fechado à força) o Início e a barra de abas oferecem "Continuar treino" a partir do banco local.
- **Estado de sincronização global (E08-07):** `useSyncStatus()` (em `LocalDataProvider`) junta a fila e a conexão num estado só, em ordem de gravidade: **Conflito — revisar** (há operação rejeitada ou em conflito), **Offline — salvo neste dispositivo**, **Pendente de sincronização** (com conexão, ainda sendo enviado) e **Sincronizado**. A conexão vem do último envio que falou com o servidor (vale mais que a informação de quando o app abriu). `SyncBanner` mostra o indicador (ícone + texto) e o que ele significa para os dados, com "Tentar novamente" quando fica pendente; o modo compacto (só o indicador) está no executor. O Início usa a versão completa.
- **Revisão de conflitos (E08-05, TEL-050):** rota `/sincronizacao` (botão "Revisar registros" no aviso de conflito). Lista o que o servidor não aceitou, agrupado por treino, com o motivo em linguagem simples e, num conflito de série, **os dois lados** ("Neste dispositivo: 60 kg × 10" / "No servidor: 55 kg × 8"). Escolhas: **Manter o meu** (reenvia a série com horário novo, que vence a do outro aparelho — última escrita vence, D-04), **Usar o do servidor** (a cópia do aparelho passa a ter os valores dele), **Tentar de novo** (recusas que podem ser passageiras), **Descartar** (só aquele registro) e **Descartar este treino do aparelho**. Descartar sempre pede confirmação e diz o efeito; nada some sozinho. Reenviar usa sempre um `operacao_uuid` novo (o servidor guarda o resultado de cada um e repetiria a recusa). Quando a revisão esvazia um treino, ele passa a "confirmado". O que o servidor tinha fica na fila (migração local 3, `estado_servidor`). Lógica em `src/data/sync/review.ts`.
- **Sair da conta com dados pendentes (E08-09):** o "Sair" do Perfil primeiro **tenta enviar** a fila (precisa da sessão ainda válida, por isso vem antes de sair). Se tudo foi enviado, sai. Se sobrou algo (sem conexão, ou registros que o servidor recusou), **não sai sozinho**: mostra quantos registros ficam e oferece "Tentar enviar agora", "Revisar registros", **"Sair e manter no aparelho"** (ficam guardados e voltam a ser enviados quando esta conta entrar de novo aqui) e **"Sair e apagar do aparelho"** (perda definitiva, com confirmação). Se não conseguir nem ler a fila, também não sai. **Troca de conta:** tudo no banco local é separado por usuário, então outra conta no mesmo aparelho não vê nem envia os registros pendentes da anterior. Lógica em `features/shell/useLeave.ts`.
- **Reconciliação depois do envio (E08-06):** quando a fila termina de enviar e um treino fica confirmado, `createReconciler` (`src/data/sync/reconcile.ts`) relê o treino do servidor e troca a cópia local pela dele (duração calculada, revisões, ajustes do servidor) e atualiza o programa ativo e os últimos registros guardados. É o "MVP alternativo" do Doc 05 §10.2 (snapshot, sem delta sync). Não mexe em treino em andamento nem em treino que tenha operações na fila (a cópia local tem o que o servidor ainda não viu); é melhor esforço, então sem rede a cópia local continua valendo e, ao abrir o treino com rede, a leitura normal a atualiza.
- **Pausar, retomar e descartar o treino (E07-08):** no executor, "Pausar treino" / "Retomar treino" (o tempo parado não conta na duração, que é calculada descontando as pausas) e "Descartar treino" (cancela, com confirmação, e volta ao Início). Funcionam sem rede pela mesma fila (`sessao_pausa` criar/atualizar e `sessao_treino` cancelar). "Finalizar" com séries pendentes já é a finalização parcial.
- **Contrato do `/sync/push` em teste:** `src/data/sync/contract.ts` espelha o que o servidor aceita em cada operação (campos permitidos, `sessao_uuid` obrigatório nas operações de série e pausa, `tipo` coerente com `ficha_uuid` na criação). Os testes do executor local primeiro falham se o app montar uma operação que o servidor recusaria. Isso foi acrescentado depois de se achar que as operações de série saíam sem `sessao_uuid` e a criação de treino de ficha saía sem `tipo`, o que o servidor rejeitaria.
- **Nova tentativa automática:** o app não recebe aviso de que a rede voltou, então, enquanto houver registro esperando na fila, tenta enviar a cada 30 s (além de ao abrir, ao voltar ao primeiro plano e após cada registro). Sem rede, o aviso de offline também oferece "Tentar novamente".
- **Contrato app ↔ servidor com a API real:** o Jest (`src/data/contract/appSyncFixture.test.ts`) roda o executor sem rede de verdade e grava a fila que o app montou em `backend/tests/fixtures/app-sync-ops.json` (um treino de ficha completo, com série extra, pausa e conclusão, e um treino avulso descartado). O PHPUnit (`AppSyncContractTest`) empurra esse mesmo arquivo no `POST /sync/push` **real**, com MySQL, trocando os UUIDs do catálogo e da prescrição pelos do programa criado no teste e deslocando os horários para o presente. Se o app mudar o que envia, o Jest falha até a fixture ser regenerada (`UPDATE_CONTRACT_FIXTURE=1 npx jest appSyncFixture`), e aí o PHPUnit passa a testar o novo formato. Conferido por mutação: tirar `tipo` da criação ou `sessao_uuid` de uma série faz o teste do servidor falhar.
- **Rótulo da carga por convenção e unilaterais (E07-10, CAT-10):** a API passou a devolver `convencao_carga` e `unilateral` em todo exercício (lista, ficha, sessão, alternativas e detalhe). O executor mostra uma legenda sob o nome do exercício quando há algo a esclarecer ("Carga em kg por halter · Repetições por lado"), e os campos e botões falam a mesma coisa para o leitor de tela ("Carga em kg por halter, série 1 de …", "Repetições por lado…"). O resumo da sessão usa a mesma unidade ("Série 1: 20 kg por halter × 10 por lado"). Convenções: `total` kg (total), `por_halter` kg por halter, `por_lado` kg por lado, `selecao_maquina` kg (máquina), `adicional_corporal` kg extra, `assistencia` kg de assistência; sem convenção informada, vale o padrão da modalidade. O volume continua sendo carga × repetições como registrado. Lógica em `features/workout/loadLabels.ts`.
- **Substituir e acrescentar exercício (E07-07):** no executor, "Substituir exercício" abre a escolha do substituto; o que já foi registrado fica no exercício original, as séries que faltam passam para o novo (que entra logo depois, guardando o exercício previsto no início), igual ao servidor. Acrescentar e substituir funcionam também quando a conexão cai depois de o treino estar no aparelho (vão para a fila como `sessao_exercicio`). **A busca no catálogo sempre precisa de conexão**: sem rede dá para trocar ou acrescentar só um exercício já escolhido antes da queda. Um treino concluído sem rede aparece no Início e no histórico até o servidor confirmar.
- **Dependências do banco:** `expo-sqlite` exige `expo-asset` (já instalado); sem ele o app nem empacota.

## Abas (E04-03)

- **Estrutura:** `src/app/(tabs)` tem as quatro abas fixas do Doc 03 §3.1: Início, Treinos (`/programas`), Evolução e Perfil. Telas de detalhe, edição e execução ficam no stack da raiz, por cima das abas (a barra some nelas). A barra é própria (`features/shell/AppTabBar.tsx`), com texto sempre visível e alvo de toque mínimo.
- **Voltar ao treino:** enquanto houver sessão aberta, a barra mostra o botão "Voltar ao treino" em qualquer aba (UX-02). A consulta roda ao montar e a cada mudança de aba ou de rota; se falhar, o botão só não aparece.
- **Perfil:** traz o nome, a verificação do tema e Sair (que saíram do Início).

## Evolução e histórico (TEL-030/031)

- **Aba Evolução:** escolha entre 4 e 12 semanas (a semana atual conta como a última). Mostra treinos, tempo de treino, séries e volume do período (`GET /me/progresso/resumo`, com o fuso do aparelho), a frequência por semana em barras com rótulo falado e a explicação do volume (indicador de acompanhamento, não nota). Sem metas, sem comparação e sem ranking.
- **Histórico:** sessões concluídas, mais recentes primeiro, paginadas ("Carregar mais"); tocar abre o resumo da sessão (`treino/[uuid]/resumo`) com os registros de cada série. Sem treino ainda, mostra um estado vazio.
- **Falhas:** resumo e histórico carregam separados; se algum falhar, aparece o aviso com "Tentar de novo". Ao voltar de outra tela a aba atualiza sozinha. Lógica em `features/progress/progress.ts`.
- **Explicação do volume (E09-04):** sob o volume, tanto na Evolução quanto no resumo da sessão, a frase curta fica sempre visível e **Como calculamos o volume** abre o detalhe: a conta (carga × repetições das séries de trabalho feitas, com exemplo), o que não entra (aquecimento, tempo, assistidos, séries sem carga), por que comparar só o mesmo exercício (a carga vale como registrada: por halter, total, máquina) e que não é nota nem meta. Período sem nenhuma série com carga mostra "—" no volume, com texto falado claro, em vez de "0 kg". Os estados vazios da Evolução e do histórico já existiam (E09-03). Componente: `features/workout/VolumeExplainer.tsx`.
- **Fora desta entrega:** gráfico por exercício e tendências (E13-01) e leitura offline do histórico (E08).

## Estados padrão das telas (E04-06, Doc 03 §9.1)

- `src/design-system/States.tsx` reúne os estados que toda tela de dados precisa: **LoadingState** (indicador + texto anunciado ao leitor de tela, sem bloquear a navegação), **EmptyState** (explicação e próximo passo), **ErrorState** (mensagem clara + "Tentar de novo"; `warning` quando só um bloco falhou, `primary` quando é a tela inteira), **OfflineState** (últimos dados e pendências locais) e **PermissionState** (por que não pode e o que pode fazer). Todas as telas de dados (Início, Treinos, detalhe e editor de programa, ficha, executor, resumo, Evolução, biblioteca, detalhe do exercício e revisão de conflitos) usam estes componentes.
- **Regra mantida por teste:** `design-system/states.test.tsx` varre `src/features` e falha se alguma tela voltar a montar na mão o "carregando" ou o par "aviso de erro + Tentar de novo". Telas novas devem usar os componentes.
- O formulário não se perde no erro: as telas de edição mantêm o que foi digitado e só mostram o aviso por cima (o editor também guarda rascunho local, E06-07).

## Rascunho local do editor de programa (E06-07, D-03, UX-17)

- **Guarda sozinho:** a cada alteração (com espera de 0,5 s, e ao sair da tela) o editor grava no aparelho o que foi montado e ainda não foi salvo no servidor (`data/cache/editorDrafts.ts`, junto da versão e da revisão do servidor sobre as quais a pessoa trabalhava). Salvar com sucesso, ou voltar a ficar igual ao servidor, apaga o rascunho. Assim, voltar pelo botão do sistema, fechar o app ou ficar sem conexão **não perde** o trabalho — editar a estrutura continua exigindo conexão para salvar e publicar (D-03).
- **Ao reabrir:** se o programa continua no mesmo ponto do servidor, o rascunho é aplicado e aparece "Recuperamos suas alterações não salvas, guardadas neste aparelho em dd/mm hh:mm", com **Descartar alterações**. Se o programa **mudou no servidor depois** do rascunho (ou a versão é outra), **nada é aplicado sozinho**: aparece "Rascunho antigo neste aparelho" e a pessoa escolhe **Usar meu rascunho** (substitui a versão atual ao salvar) ou **Descartar rascunho**. Isso evita sobrescrever em silêncio uma mudança feita em outro lugar.
- **Sair:** com alterações, o diálogo diz que elas ficam guardadas no aparelho ("Sair e guardar rascunho"); **Descartar alterações** (com confirmação) volta à versão do servidor. Sem banco local aberto, o editor funciona como antes (mensagem "Sair sem salvar?").
- **Sair da conta:** o rascunho segue a regra dos demais dados locais (ver E08-09): fica no aparelho se a pessoa escolher manter, e é apagado se escolher apagar.

## Cópia de programa (E06-09)

- No detalhe de qualquer programa, **Criar cópia** (para programa de coach: **Criar minha cópia para editar**, em destaque, com o aviso de que o original não pode ser editado). Pede confirmação dizendo que o original não muda, cria um programa **novo, seu** (origem "Criado por você", `derivado_de` apontando para o original) com as fichas da versão vigente e abre a cópia. A API é a `POST /programas/{uuid}/copiar` (E06-01), com chave de idempotência (repetir por engano não cria duas). Erro de rede e erro genérico avisam e deixam tentar de novo. É o caminho previsto pela RG-005 para personalizar o que veio de um coach.

## Biblioteca de exercícios (E06-06, TEL-024/025)

- **Onde fica:** não é uma aba (Doc 02: a biblioteca é acessada em contexto). Entradas: botão "Biblioteca de exercícios" na aba Treinos (`/exercicios`); botão **Detalhes** em cada exercício ao escolher exercício para a ficha ou para o treino; e **Como fazer este exercício** no executor.
- **Biblioteca:** busca por nome (com pequena espera ao digitar), filtro por grupo muscular e por equipamento, lista paginada ("Carregar mais"), estado vazio com "Limpar busca e filtros" e erro com "Tentar de novo". Se os filtros não carregarem, a lista funciona sem eles. É só leitura e só mostra exercícios publicados.
- **Detalhe (`/exercicios/[uuid]`):** tags (equipamento, modalidade, dificuldade, unilateral), **Demonstração**, **Como fazer** em passos numerados, **Cuidados**, músculos principais e secundários e **Alternativas** (cada uma abre o detalhe dela).
- **Fallback textual (UX-10, AC-10):** a demonstração só aparece se a API devolver mídia **aprovada**. Com imagem aprovada, mostra a imagem e "Demonstração revisada · versão N"; se a imagem não carregar, cai no aviso e segue com o texto. Vídeo/animação aprovados avisam que ainda não abrem no app (o player é a E10-09). Sem mídia, avisa que não há demonstração e mostra as instruções. Instruções ausentes viram "ainda estão em revisão". O registro do treino nunca depende da mídia.
- **Fora desta entrega:** player de vídeo com cache e legendas (E10-09) e leitura da biblioteca sem conexão.

## Início (TEL-010)

- **O que mostra:** saudação, estado de sincronização (`SyncStatus`), e por prioridade: **treino em andamento** (Continuar), **próxima ficha do programa ativo** (Iniciar / Ver a ficha) ou, sem programa, **Criar programa**; depois "Sua semana" (segunda a domingo no fuso do aparelho, `WeekStrip`), treinos e tempo de treino da semana (`StatTile`) e a última sessão.
- **Dados:** três chamadas em paralelo (sessão aberta, programa ativo, sessões concluídas recentes). Cada uma falha sozinha: o resto aparece, um aviso oferece "Tentar de novo" e o treino avulso continua disponível. Ao voltar de outra tela o resumo atualiza sem piscar.
- **Próxima ficha:** a que vem depois da ficha do último treino concluído do programa (volta à primeira depois da última); sem histórico, a primeira. Ficha sem exercício fica fora da rotação. Lógica em `features/home/home.ts`.
- **Fora desta entrega:** convite de coach pendente (Fase 3), fila de sincronização real no `SyncStatus` (E08: hoje só "Sincronizado" ou "Offline") e volume semanal (depende do resumo da E09).

## Executor de treino (TEL-012)

- **Fluxo:** Início → "Iniciar treino avulso" (ou "Continuar treino em andamento" se já houver um aberto: o servidor aceita só um por vez) → `treino/[uuid]` → `treino/[uuid]/exercicios` (escolha de exercício do catálogo, que já cria 3 séries). Finalizar volta ao Início.
- **Pré-preenchimento (D-14):** carga e repetições vêm **sugeridas** e editáveis, em cor secundária até o usuário editar; só viram registro no toque em **Concluir**. Ordem da sugestão: série anterior já concluída neste treino → série de mesma posição (ou a última) do último treino concluído do exercício → em branco. Corrigir uma série concluída reabre os campos e registra de novo.
- **Validação local = servidor:** carga e repetições (`reps_carga`), só repetições (peso corporal e assistido; carga opcional) ou só duração (`tempo`). Carga aceita vírgula (`42,5`).
- **Lógica fora da tela:** `features/workout/input.ts` (digitação), `prefill.ts` (sugestão), `workoutApi.ts` (chamadas) e `useWorkout.ts` (estado). Esta entrega é **online**: salvar offline e a fila de sincronização são as histórias E08-01…E08-03.
- **Descanso (TEL-013, `features/rest/`):** o timer guarda o **instante final** (`restTimer.ts`, funções puras), não um contador: bloquear a tela ou trocar de app não faz o tempo parar, e ao voltar o relógio é recalculado na hora. Inicia ao concluir uma série nova (configurável; corrigir não reinicia) ou à mão; pausar, pular e ajuste de 15 s (limites de 15 s a 10 min); padrão 90 s. Não bloqueia: dá para editar outras séries durante a contagem. Fim: háptico (uma vez) e aviso local agendado (`expo-notifications`), cancelado ao pausar, pular ou sair da tela. A permissão de notificação é pedida **uma vez**, quando o primeiro descanso começa; sem permissão, o descanso segue só dentro do app. Leitor de tela: o texto de apoio (região viva) muda a cada 15 s, não a cada segundo.
- **Resumo (TEL-014, `treino/[uuid]/resumo`):** ao finalizar, o executor abre o resumo, que **relê a sessão no servidor** e só mostra "Treino concluído!" se ela estiver concluída (senão avisa e deixa tentar de novo). Mostra duração (ativa, sem pausas), séries concluídas de total, exercícios executados e, se houver carga, o volume. **Volume = carga × repetições das séries realizadas de trabalho** (sem aquecimento, sem exercício de tempo ou assistido, só com carga maior que zero), a mesma regra do servidor; a tela explica o cálculo e que não é nota do treino. "Ver registros" expande as séries feitas. Lógica em `features/workout/summary.ts`.
- **Meus treinos (TEL-020, `features/programs/`):** abas **Ativo** (programa em uso primeiro, depois os outros publicados), **Rascunhos** e **Arquivados**, com contagem; cada cartão (`WorkoutCard`) mostra a **origem** (`OriginBadge`: ícone + texto + cor, nunca só a cor), versão e data, e o ativo mostra "Em uso" e as fichas. "Criar programa" abre `programas/novo` (nome até 180, objetivo até 100; a chave de idempotência é da tela, então tentar de novo não duplica) e leva ao detalhe `programas/[uuid]`, por ora **somente leitura** (fichas e exercícios; a edição é a E06-04). Ativar, arquivar e copiar são a E06-08/E06-09; "Receber sugestão" é da Fase 2. A lista carrega até 500 programas (5 páginas de 100).
- **Editor de programa (TEL-021/022/023, `features/programs/editor/`):** "Editar programa" no detalhe abre `programas/[uuid]/editar`, um grupo de telas que **compartilham um rascunho em memória** (`ProgramEditorProvider` no layout do grupo): programa (nome, objetivo, fichas: ordem, duplicar, remover) → ficha (nome, exercícios: ordem, remover, adicionar pela busca do catálogo) → configurar exercício (séries de trabalho, aquecimento opcional, faixa de repetições, carga-alvo, RIR, descanso, observações; exercício de tempo usa a duração). **Salvar rascunho** envia a estrutura inteira com a revisão que o app conhece (`PUT .../estrutura`); outra edição no meio do caminho vira `409` e o app avisa em vez de sobrescrever (botão Recarregar). **Publicar versão** confirma, salva antes e publica; publicar não ativa o programa. Programa publicado abre uma nova versão em rascunho; do coach ou arquivado não abre. Modelo, redutor e validação são puros e testados (`model.ts`, `reducer.ts`): as mesmas regras do servidor (14 fichas, 30 exercícios por ficha, 20 séries por exercício, repetições 1–1000 com mínimo ≤ máximo, RIR 0–10, descanso 0–3600 s). O formulário aplica os **mesmos parâmetros a todas as séries de trabalho** (séries preparatória ou dropset vindas de outra origem só são trocadas ao tocar em Aplicar). Há aviso ao sair com alterações pendentes pelo botão Voltar; o gesto/botão de voltar do sistema e o **rascunho local** que sobrevive ao fechar o app são a E06-07.
- **Ativar, trocar e arquivar (FL-07, `ProgramDetailScreen`):** no detalhe do programa. **Ativar** vale para a versão publicada vigente e é direto quando não há programa em uso; havendo outro, o app **pergunta antes de trocar** e diz que o atual continua guardado. Programa em rascunho não ativa (o app orienta a publicar); o que já está em uso mostra o aviso e não oferece ativar de novo. **Arquivar** pede confirmação, explica que o histórico de treinos é preservado e que **não há desarquivar**; se for o programa em uso, avisa que o aluno fica sem programa ativo (dá para treinar avulso ou ativar outro). Programa do coach pode ser ativado (o servidor exige o aceite), mas não editado; arquivado não tem ações. Nada disso altera treinos já feitos (AC-07).
- **Detalhe da ficha e treino programado (TEL-011, `FichaDetailScreen`):** no detalhe de um programa **publicado**, cada ficha tem "Abrir a ficha …" (rascunho não inicia treino). A tela mostra a origem, os exercícios e a prescrição legível (ex.: `3 × 8–12 + aquecimento · descanso 1:30`) e o botão **Iniciar {ficha}**, que cria a sessão a partir da ficha (`POST /me/sessoes` com `ficha_uuid`; o servidor copia exercícios e séries prescritas). O servidor aceita **um treino aberto por vez**: se o aberto é desta ficha o botão vira **Continuar este treino**; se é avulso ou de outra ficha, a tela avisa e só oferece continuar aquele. Se não der para consultar o treino aberto (rede), a ficha ainda abre e o iniciar tenta; um 409 devolve o treino já aberto.
- **Metas da prescrição no executor (D-14):** quando o treino nasce de uma ficha, o executor busca a versão do programa (`GET /programas/{id}/versoes/{n}`) e liga cada série à sua meta pelo `serie_prescrita_id`. A sugestão de valores segue, nesta ordem: o que já foi registrado na série; a **série anterior concluída do mesmo tipo** neste treino; e, campo a campo, a **meta com o último treino de apoio** — a **carga-alvo manda** quando existe (senão vale a carga do último treino), as **repetições partem do último treino** (ou do mínimo da faixa, sem histórico) e ficam sempre **dentro da faixa** (15 numa meta de 8–12 sugere 12), e a **duração** (exercício de tempo) segue a meta. **Aquecimento** não herda a carga de trabalho. A tela mostra "Meta: 8–12 repetições · 60 kg" quando as séries de trabalho têm a mesma meta. Se a busca das metas falhar, o treino segue só com o último registro; o valor continua sendo referência até o toque em Concluir. Lógica em `prefill.ts`; metas por `workoutApi.programTargets`.
- **Fora desta entrega:** duração de descanso por exercício (vem da prescrição, E06-05) e preferências de descanso e háptico persistidas (E04-05), substituir exercício e pausar (E07-07/E07-08), resumo da sessão (E07-09) e rótulos de carga por convenção (E07-10).
